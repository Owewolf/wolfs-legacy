# Email reply check-in threat model

Prepared before email implementation on 28 October 2026, against the local Wolf's Legacy branch and `Wolfs_Legacy_Email_Integration_Reply_2FA_Implementation_Brief.md`. This is a security design and review checklist; it is not evidence that a real provider round trip has passed.

## Baseline and protected state

The inspected baseline has no mail worker or notification tables. SQLite stores encrypted vault fields, encrypted HomeBank snapshots, managed-document metadata, hashed beneficiary access tokens, owner credentials, Dead Man's Switch configuration and audit records. `server/routes/deadswitch.js` permits authenticated check-in and configuration changes. `server/index.js` checks final expiry at startup and hourly. A release grants access to beneficiaries; the public beneficiary access route can also grant access after its independent emergency waiting period or a triggered switch. Manual grant, revoke and emergency denial are separate owner operations. Existing check-in clears the switch's triggered state but does not revoke a beneficiary's existing grant or cancel emergency requests.

The email feature must protect `last_check_in`, immutable cycle identity, release deadline, one-time codes, recipient verification, beneficiary permissions, vault/document contents, transport credentials and audit integrity. An email failure must never change check-in or release state. A check-in must never cancel a separate emergency request, modify its waiting period, or revoke an existing grant. A late email must never undo a release.

## Trust boundaries

1. The authenticated owner browser provisions and rotates independent recovery codes. Treat the one-time response as secret. It must not enter email, routine logs, URLs or browser analytics.
2. SMTP and IMAP servers are external systems. TLS authenticates transport peers and protects transport; it does not prove that a human approved a check-in. SMTP acceptance is `sent_to_server`, not confirmed delivery.
3. MIME content and headers are attacker-controlled. Neither `From`, `Reply-To`, a display name, forwarding headers nor an untrusted `Authentication-Results` header independently authenticates the owner.
4. SQLite is the durable authority for unique jobs, challenge and recovery-code hashes, mailbox checkpoints, one-time consumption and cycle transitions. External SMTP cannot join a SQLite transaction, so a crash after provider acceptance has an unavoidable delivery ambiguity that must be surfaced and handled explicitly.
5. The host, `.env`, generated `data/.secrets`, database snapshots and independent offline code storage are sensitive. A database restore can revive old credentials and queued mail unless deliberately quarantined.

## Threats and required controls

| Threat | Required control and verification |
| --- | --- |
| Mailbox compromise | Every accepted email requires both a fresh reminder challenge and an independently stored unused code. Verify the owner notification address before enabling replies. Challenge alone must fail. Store the offline batch outside this inbox; downloading it into the same synced mailbox defeats factor separation. |
| Stolen offline code | A code alone must fail without a current owner/cycle-bound email challenge. Store only hashes or keyed digests; rotate all unused codes through an authenticated owner operation. Show plaintext only once. |
| Forged sender or forwarded reminder | Bind challenge to an owner, verified address and cycle; require a single expected originating address and corroborating reply metadata. Reject automatic and forwarded messages. Check trusted provider authentication metadata when available, but never count it as the independent factor. Warn the verified owner only, never an arbitrary supplied sender. |
| Replay, concurrency or duplicate mailbox delivery | Deduplicate by mailbox UID validity/UID and stable message identity. In one SQLite transaction, validate current active unreleased cycle, consume challenge and recovery code, reset check-in, invalidate old-cycle work, record audit and queue acknowledgement. Uniqueness constraints and conditional updates must prevent two acceptances. |
| Expired or superseded challenge | At most 24 hours validity, capped at final release deadline. New reminders supersede older challenges; templates must say to use the newest challenge. Check actual processing time, not an attacker-controlled `Date` header. Deny if disabled, released, expired or cycle changed. |
| Brute force and email flood | High-entropy codes, constant-time digest checks where feasible, bounded message parsing, per-owner failure controls and rate-limited security warnings. Never disclose which factor failed. Limit worker batches and preserve checkpoints only after durable processing. |
| Malicious MIME, attachments and HTML | Parse a bounded plain-text body. Do not execute HTML, load remote images or process attachments. Ignore quoted text/signatures; require exactly one unambiguous `CONFIRM` line and reject conflicting lines, automatic messages and malformed bodies. Bound raw-message size before parsing. |
| Log injection or secret disclosure | Log fixed reason codes and internal IDs. Never log raw MIME, either code, SMTP/IMAP passwords, bearer/access tokens or sensitive vault content. Sanitize provider error responses and newline-bearing fields. Escape template interpolation and provide accessible plain text. |
| Webhook replay | The chosen implementation uses read-only IMAP. A later webhook adapter must verify the provider signature with replay/time checks and deduplicate stable identities before it can call the shared verifier. An unauthenticated inbound HTTP endpoint is out of scope and must not be added. |
| Schedule duplication or time changes | Persist immutable cycle ID, UTC release deadline and five ordinal reminder jobs, unique per cycle. Compute final expiry from interval plus grace. This implementation accepts only `Africa/Johannesburg` for scheduling and presentation. Reconcile only upcoming reminder slots; never backfill several reminders in a day or release early. Test restart and configuration changes. |
| SMTP outage or ambiguous send | Require verified TLS (587 STARTTLS or 465 implicit TLS), bounded timeouts, durable attempts, retries and dead letters. Persist operational health and distinguish queued, provider-accepted, independently delivered, failed and retried states. Never treat mail submission as an owner check-in. |
| IMAP outage, UID reset or old mail | Use a read-only mailbox connection and explicit durable message tracking, including UID validity. Reconnect and resume without deleting mail. Recovered messages are valid only if their codes remain valid at verification time. Report repeated failures through persistent status and an independent channel when configured. |
| Restore replays historical jobs/codes | Stop service, preserve a complete pre-change snapshot, restore into a separate copy and quarantine mail before any worker starts. Disable notification/reply settings, cancel restored pending mail, revoke challenges and offline codes, and require owner verification plus a newly issued independent batch before re-enabling. Preserve access state and encrypted vault data. |
| Privilege or host compromise | Restrict `.env`, `.secrets`, database and recovery material to the service account/root. Use a non-root systemd process, restart supervision and the intended working directory. Keep port 4444 behind intended access controls/TLS. Host/root or owner-session compromise remains outside what the email protocol can prevent. |

## Acceptance review

Verify factor isolation, malformed/forwarded/automatic messages, wrong owner/cycle, expiry boundary, duplicate and concurrent arrivals, already released state, supersession, failed transaction rollback, SMTP retry/dead-letter behavior, IMAP failure recovery, one reminder per local day, and restore quarantine with tests that inspect resulting database state. Confirm migration preserves vault ciphertext, HomeBank/document mappings and beneficiary token hashes.

Real-provider acceptance additionally requires sending a configuration test, verifying the recipient, issuing offline codes into separate storage, receiving a real two-code reply, inspecting the old and new cycles and transport/audit records, and confirming the owner acknowledgement in the mailbox. Do not place either code or provider credentials in evidence committed to Git. Until that exercise is performed with configured credentials, real end-to-end acceptance remains pending.
