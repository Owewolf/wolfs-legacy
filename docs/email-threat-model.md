# Email check-in threat model

Updated on 28 October 2026 to match the owner's simplified workflow in the [implementation brief](Wolfs_Legacy_Email_Integration_Reply_2FA_Implementation_Brief.md): verify the notification email once, select **Confirm I’m here** in a reminder, and send the prefilled email. This document describes the security boundaries and review criteria; real-provider acceptance evidence is recorded separately in the [test report](email-test-report.md).

## Baseline and protected state

The preimplementation baseline had no mail worker or notification tables. SQLite stores encrypted vault fields, encrypted HomeBank snapshots, managed-document metadata, hashed beneficiary access tokens, owner credentials, Dead Man's Switch configuration and audit records. Authenticated owner check-in and configuration changes remain available. Final release is checked at startup and hourly. A release grants beneficiary access; the beneficiary route can also grant access after its independent emergency waiting period or a triggered switch. Manual grant, revoke and emergency denial are separate operations. Normal check-in does not revoke an existing grant or cancel an emergency request.

The email feature protects `last_check_in`, immutable cycle identity, release deadlines, single-use confirmations, recipient verification, beneficiary permissions, vault/document contents, transport credentials and audit integrity. Invalid mail, transport failures and delivery status cannot change check-in or release state. An accepted confirmation resets only the timer and starts its next cycle. It leaves the switch enabled, grants no vault session or permission, cancels no independent emergency request, alters no beneficiary waiting period and revokes no prior grant. A late email cannot undo a release.

## Chosen authorization model

Email check-in is **not two-factor authentication**. The verified mailbox is the owner's chosen authorization factor for resetting this timer. A person with access to that mailbox and a current reminder can submit a check-in. This does not provide vault access: viewing or changing vault contents still requires the normal account authorization. No independent code batch or storage attestation is part of enrollment or confirmation.

One-time address verification occurs in the authenticated owner session. It automatically enables email check-ins without moving `last_check_in`. Changing the recipient requires the vault password and new email verification. Optional notification-policy changes also require the vault password. Routine reminders require neither a password nor another address verification.

The reminder's **Confirm I’m here** button uses `mailto:` to prepare a message. Only receipt and validation of the sent message can reset the timer. Opening an email, loading an image, making an HTTP GET, selecting the button or running an email link scanner cannot perform that transition.

## Trust boundaries

1. The authenticated owner browser establishes the notification recipient and optional preferences. The one-time verification value and account password remain out of routine logs and browser storage.
2. SMTP and IMAP are external systems. Certificate-verified TLS protects the transport and authenticates its server; it does not prove that a human sent a confirmation. SMTP acceptance is `sent_to_server`, not independently confirmed delivery.
3. MIME content and headers are untrusted. A `From` address, display name, `Reply-To`, forwarded header or arbitrary `Authentication-Results` header is insufficient alone. The service also requires a current high-entropy confirmation bound to the verified owner, cycle and reminder.
4. SQLite is the authority for unique jobs, confirmation digests, mailbox checkpoints, one-time consumption and cycle transitions. SMTP cannot join its transactions; a crash after provider acceptance may leave an uncertain send that requires inspection.
5. The host, `.env`, generated `data/.secrets` and backups are sensitive. Restore quarantine is required before starting workers on a restored mail database.

## Threats and controls

| Threat | Control and verification |
| --- | --- |
| Forged sender or copied/forwarded reminder | Require the verified originating address, expected reply mailbox and valid unused owner/cycle-bound confirmation. Reject forwarding and automatic replies. A direct reply must match the reminder thread. A button-created new message may omit thread headers only with the exact fixed subject `Wolf's Vault check-in confirmation`, expected mailbox, verified sender and bound confirmation. |
| Token disclosure | Confirmation values expire within 24 hours and no later than final release; newer reminders supersede older values. SQLite stores digests and nonsecret derivation IDs rather than plaintext. Do not log raw MIME, confirmation values or reminder bodies. Mailbox access remains sufficient authorization under the chosen model. |
| Mail prefetch or scanner activation | No state-changing HTTP route is linked from reminders. The `mailto:` button only prepares a message; the inbound verifier alone performs the transaction after actual receipt. |
| Replay, concurrent replies or duplicate mailbox delivery | Deduplicate by UID validity/UID and stable message identity. Atomically validate the active unreleased cycle, consume a protocol-2 confirmation once, reset check-in, invalidate old work, append audit and queue acknowledgement. Conditional updates and database uniqueness prevent double acceptance. |
| Legacy challenge reinterpretation | The migration marks old challenges as protocol 1, revokes unused ones and cancels their pending sends. New reminders are protocol 2. Never accept a legacy two-code challenge as a simple confirmation. Revoke unused legacy recovery-code rows while retaining their history; provisioning is retired. Preserve verified addresses and owner preferences. |
| Expired, superseded, wrong-owner or disabled cycle | Validate actual processing time rather than the email's `Date`. Reject expired/revoked confirmations, inactive or released cycles, disabled replies, wrong owner and changed cycle. A late arrival never reverses release or permissions. |
| Brute force and mail flood | Use high-entropy confirmation values, digest comparisons, bounded parsing, per-owner failure controls and throttled owner warnings. Report generic failure details. Limit worker batches and advance checkpoints only after durable processing. |
| Malicious MIME, HTML and attachments | Parse bounded plain text or safely convert bounded HTML-only replies without executing markup or loading remote content. Ignore quoted content and signatures; require exactly one unambiguous current confirmation. Reject conflicting lines, nested forwarded messages and automatic messages. Do not execute or open attachments. |
| Forged authentication result | Trust only configured receiver-owned `Authentication-Results` identifiers whose header-stripping boundary is established. Reject reported authentication failures from that trusted boundary. Missing/untrusted results do not replace confirmation validation, and no domain-authentication pass is claimed from absent headers. |
| Log injection or secret leakage | Log fixed reason codes and internal IDs. Keep raw provider errors, MIME, confirmation values, SMTP/IMAP credentials, bearer/access tokens and vault data out of routine logs. Escape template interpolation; include an accessible plain-text version and no trackers/external images. |
| Webhook replay | The implementation uses read-only IMAP. Any later webhook adapter would need signature, freshness and deduplication checks before reaching the shared verifier; there is no unauthenticated inbound HTTP route. |
| Duplicate reminders or time changes | Persist cycle identity, UTC expiry and five ordinal jobs with uniqueness constraints and a per-local-date send ledger. Compute expiry from interval plus grace in `Africa/Johannesburg`. Reconcile upcoming slots only; never backfill several reminders in one day or release early. |
| SMTP outage or ambiguous send | Require certificate-verified STARTTLS on 587 or implicit TLS on 465, bounded timeouts, durable attempts, retries and dead letters. Persist health and distinguish queued, accepted, independently delivered, failed, retried and uncertain states. No submission or failure counts as a check-in. |
| IMAP outage, UID reset or recovered old mail | Use read-only retrieval and durable UID/fingerprint tracking. Resume after restart without marking, deleting or moving messages. Recovered mail is valid only if the confirmation and cycle remain valid at processing time. Surface degraded status and use the independent alert channel when configured. |
| Restored historical jobs or confirmations | Stop workers, preserve a full snapshot, restore to a separate copy and quarantine before startup. Disable replies, clear recipient verification, cancel pending mail, revoke confirmations and legacy recovery-code rows, and supersede open cycles. After review, one fresh address verification enables replies again. Preserve encrypted data, access state and history. |
| Host or owner-session compromise | Restrict secrets and databases to the non-root service account/root. Use systemd supervision, the intended working directory and access controls around port 4444. Host/root or authenticated owner-session compromise exceeds the email protocol's protection boundary. |

## Acceptance review

Inspect database state for the normal prepared-email path, direct threaded replies, malformed/forwarded/automatic mail, missing or conflicting confirmations, forged sender, wrong mailbox/subject/thread/owner/cycle, supersession, expiry boundary, replay and concurrency, released state and transaction rollback. Verify that opening a reminder or resolving its prepared-mail action cannot call a timer-changing HTTP route. Confirm one reminder per local day, retries/dead letters, persistent health, restart/IMAP recovery and restore quarantine. Compare preexisting vault ciphertext, HomeBank/document mappings and beneficiary token hashes across migration.

Real-provider acceptance requires a verified recipient, actual reminder delivery, selecting its button and sending the prepared email through the configured provider, exactly one durable accepted confirmation, the expected old/new cycle state and the acknowledgement observed in the mailbox. Preserve sanitized evidence only. The earlier template-preview campaign does not prove the revised confirmation round trip.
