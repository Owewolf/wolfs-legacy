## Storage and authorization decisions before implementation

1. Use separate `legacy_contents`, recipient, attachment, link, version, review and immutable release/audit tables. Public IDs use UUIDs. Every query and association validates owner ID; references to existing beneficiaries are foreign keys. Delete a beneficiary's association, not its owner's canonical content or managed file. A single content and managed-file record can be assigned to several people.
2. Defaults are `draft` and `owner_only`, with no recipients. Valid statuses are draft, ready, released and archived. A status alone never substitutes for a recipient release record. Drafts and archived records fail all beneficiary list/direct/search/binary access paths, including formerly released records later archived or returned to draft.
3. The common beneficiary predicate requires a present, unexpired current token; current, nonrevoked global grant; owner-matching explicit active recipient association; usable lifecycle; and durable release satisfying that item's policy. `manual_release` requires explicit confirmed owner action for named recipients. `dead_switch_release` requires a confirmed trigger event. `emergency_access_release` requires explicit item opt-in plus a real emergency/manual grant under the configured waiting rules. `owner_only` always denies beneficiaries. Rechecking this predicate is mandatory for every read/range/acknowledgement.
4. Do not backfill old granted beneficiaries into new private items or release new ready items merely because a historical trigger exists. Record a release event and its qualifying event/version; repeating a scheduler or owner request must be idempotent. Editing body, changing recipients/policy and attaching new private bytes must not silently broaden a previous release. Keep revision snapshots encrypted and audit explicit releases/revocations.
5. Store file bytes once under generated managed paths and encrypted metadata in SQLite. New private attachments must have no permissive fallback through old document routes. Adding a restricted attachment association to a formerly broad document must prevent the broad beneficiary path. Owner association editing must not let another owner attach guessed file IDs.
6. Initial media types: MP3 → `audio/mpeg`; M4A → `audio/mp4`; WAV → `audio/wav`; MP4 → `video/mp4`; MOV → `video/quicktime`. Validate server bytes/container headers against extension and expected brands rather than trusting browser MIME. Keep the existing finite `DOCUMENT_MAX_FILE_MB` setting (25 MiB default, maximum 100 MiB) and at most eight files per request; expose limits in the picker. Validate non-finite/malformed configuration. Browser codec availability determines playback; authenticated download remains available.
7. Support one `bytes` range including suffix ranges; return correct 206/416 responses and never stream outside the opened descriptor's bounds. Content requests carry owner/beneficiary credentials in headers or POST bodies, never query strings. Use private/no-store, nosniff and safe dispositions; close descriptors on cancellation/errors. Do not publish thumbnails or remote image Markdown. Strip GPS/EXIF and other incidental photo metadata from newly uploaded managed photos before hashing/persisting them; never mutate the selected original. Existing photos remain unchanged and must not be described as scrubbed.
8. Reviews store last/next dates, interval, reviewer and history independently of `users.last_check_in`, switch configuration and notification cycles. Durable idempotency keys include the item and scheduled review occurrence. Snooze/reschedule/disable must cancel stale pending review jobs; owner notices contain only a generic protected-content action. Checklist acknowledgements use separate beneficiary rows and cannot edit canonical checklist text.
9. Links store existing IDs and safe relationship labels. Validate `final_wishes` parent section and owner for optional parents; links can point to property, vehicles, contacts and other same-owner visible entries. Preserve uncertain archive dates explicitly (exact, approximate, unknown) and search owner-supplied people/tags/date ranges without guessing identity or precise dates.

## Migration, backup and rollback risks

- Capture schema/ciphertext/token/document-mapping digests before/after a synthetic upgrade and re-run migration. New foreign keys must not cascade from beneficiary or optional old-entry removal to the owner's master content/files. Corrupt/partial feature schemas must fail safely rather than mark the migration applied.
- Rollback should select a matching pre-upgrade stopped snapshot and source revision in a separate checkout. Retain newer snapshots so post-upgrade owner work can be reconciled; do not drop new tables as a routine rollback or start old code against an unreviewed new database.
- The complete recovery unit is SQLite with WAL/SHM as applicable, matching `data/.secrets`, protected `.env`/notification secret/configuration, managed media tree, effective service unit and exact source revision. Loss of the encryption key loses personal text even if media survives.
- Restore only into an independent private directory for verification. Compare file checksums, encrypted text/revisions, beneficiary mappings and release/review histories; run integrity/FK checks; apply existing mail quarantine before any worker startup. Quarantine must cancel old pending review/content emails along with existing outgoing jobs without revoking legitimate content or resetting check-in.
- The production service remains `wolfs-legacy.service`, user `wolf`, port 4444. This audit does not authorize or claim a service restart, production schema upgrade or GitHub publication. Local implementation/test fixtures must not touch live data or send real mail.

## Release acceptance criteria

The implementation is releasable only with automated synthetic-fixture evidence for these checks, plus reviewable operational evidence for the final host checks:

1. Existing Final Wishes category/details/contact ciphertext and beneficiary identities/token hashes survive additive migration unchanged; migration is repeatable and FK integrity passes.
2. Every new type defaults private. Every beneficiary token fails draft/owner-only/unreleased/archived reads through lists, direct IDs, search, old full-vault serialization, old document metadata/download, new document preview and range/download APIs.
3. Beneficiary A cannot access B's content or attachment, including guessed IDs and documents shared through another legacy entry. Cross-owner mutation/link/file association attempts fail. Denials are audited without credentials/content.
4. Manual confirmed release, emergency request versus waiting/grant, and confirmed switch trigger have distinct tested outcomes. Reminders, email check-in and review cannot release content. Repeated events/releases are idempotent; late check-in preserves released state. Explicit grant/item revocation and token expiry/regeneration/deletion immediately prevent subsequent reads/ranges.
5. Many recipients reference one content/file. Removing recipients/beneficiaries or unlinking files preserves master content, other recipients and source bytes. Failed saves/uploads clean temporary copies; quota/MIME/format/path/symlink/corrupt-byte and interrupted-request handling is safe.
6. PDF/image previews and browser-supported audio/video playback work under the same authorization. Full, partial, suffix and unsatisfiable ranges return expected data/status. Unsupported codecs retain authenticated downloads. No secret URL/static route is created.
7. Markdown payloads with raw scripts, HTML/event handlers, unsafe links and external images cannot execute or contact trackers in owner or recipient previews. Encrypted DB inspection finds no synthetic plaintext body/title/people/checklist/revision markers.
8. Family archive supports explicit uncertain dates, people/tags/date search and chronological view. Instructions support multiple safe links, ordered steps and recipient acknowledgement without changes to the canonical item.
9. Reviews implement no-change, updated, reschedule, snooze and disable with durable history and deduplicated generic mail. Review state and reminders never change check-in timestamps, switch deadlines/grants, or the existing five reminder slots/current verified-mailbox reply protocol.
10. Backup/restore in an isolated directory preserves encrypted metadata, media checksums, recipient mappings, versions, review/release/audit history and matching keys. Restored pending mail is quarantined; no real mail or production writer is involved.
11. Existing HomeBank, documents, auth, email/worker and switch regression suites pass. Browser evidence covers the existing Final Wishes/Beneficiaries screens, recipient-only read view, safe preview and playback without a new top-level section.
12. Reviewed README/runbook covers Fedora/systemd, port 4444, permissions, binary plaintext limitation, limits, migration/recovery/rollback. A PR includes actual testing evidence and screenshots. Real service health/recovery/deployment are reported separately from isolated tests; no claim of production verification is made without performing it under authorization.

This report records the preimplementation findings and decisions. Completion and measured test results belong in the implementation/test report and PR; the acceptance list above is not a claim that tests already passed.
